# EDGEweb: notes for Claude sessions

EDGEweb is the website for https://edgemodders.ai, the home of EDGEmodders: a new Cyberpunk 2077 modding community whose message is **"Anyone can mod"**. AI assistants (Claude first) make modding possible for people without coding or modding skills. The site is a landing page that pitches the tools and links to their Pages sites. It is one of the EDGE platform's repos by the same owner, all at https://github.com/Edgemodders. The site covers thirteen of them: the five core toolkits REDagent (in-game modding agent), REDnode (runtime), REDcode (IDE), REDbridge (engine host, GPL-3.0) and EDGEdeck (mod manager), the specialist toolkits EDGEbuilder (world builder on REDnode), EDGEwave (sound studio), EDGEmat (material editor), EDGEquest (quest maker), EDGEhack (quickhack editor), EDGEdir (director's tool: scenes of the game's people on a timeline, with EDGE Director, its app in the game; not released yet) and EDGEkit (the editor app and its extension pack), and EDGEchat (the EDGE plugin for Claude Code, 0.1.x). Each has a wiki section, a card on the landing page and a section on the platform page. EDGEchat's and EDGEdir's cards and sections have no icon: there is none in `docs/assets/tools/` yet. EDGEdir's wiki section was written by the EDGEdir session (2026-11-20), which keeps its pages current with EDGEdir's changes; a session here still checks them against the repo when the section is touched. REDsave (save game manager, built into EDGEkit) has no wiki section; the site links its docs at https://edgemodders.github.io/REDsave/. EDGEfab (asset maker) has a wiki section and a row in the wiki home's table, but no card or platform section yet. Not covered yet: EDGEmods (mod registry, early build). REDnode's `CLAUDE.md` sets the shared conventions.

## Site

- `docs/index.html` is the landing page and `docs/platform.html` ("Read more") is the EDGE platform page. Both are standalone HTML with no front matter, so Jekyll serves them as-is, and share `docs/assets/css/site.css`. The platform is called **EDGE**; the community is **EDGEmodders**.
- `platform.html` has a benefits table with a status per row (Working, In progress, Planned) and a section per toolkit with screenshot placeholders (`.shot` divs). To fill one, put the image in `docs/assets/shots/` and replace the placeholder's contents with an `<img>` with real alt text. Re-check the statuses against each tool's CLAUDE.md whenever the page is touched.
- `docs/*.md` pages use `docs/_layouts/default.html` and `docs/assets/css/hud.css`. Add every new page to `nav` in `docs/_config.yml`.
- `docs/community.md` is the "Get involved" page: where the community lives, ways to help, ground rules. The community Discord is https://discord.gg/63qP3Erw43: `discord` in `_config.yml` (used by the layout and markdown pages) and hard-coded in `index.html` and `platform.html` (footer chip and Join button). Change all three together. The invite never expires. When `site.css` changes, bump the `?v=` on its link in both HTML pages so browsers skip their 10-minute cache (the layout versions `hud.css` automatically).
- Deployed by `.github/workflows/pages.yml`. Custom domain `edgemodders.ai` is set in Settings > Pages, not with a CNAME file (Actions deploys ignore it).
- Tool status lines on the cards come from each tool's README and CLAUDE.md. Keep them current and honest; mark anything unbuilt as such. The transcript in "The loop" is labelled illustrative and must stay labelled until the loop works end to end.

## Dashboard (the manager's view)

- `docs/dashboard.html` is the EDGE dashboard at https://edgemodders.ai/dashboard.html: every tool's build plan, last release, open requests, tests, who waits on whom, what waits on the owner, and which local Claude session works on each tool. It is not in the site's nav and is marked `noindex`. It is also the entry point for a managing session that reviews the whole platform and messages the tools' sessions.
- All its data is one file, `docs/assets/dashboard/status.js` (`window.EDGE_STATUS = {...};`, plain JSON after the `=`). The page only draws it. A session reads that file, not the page.
- `python tools/dashboard/refresh.py` rewrites what a script can read: `issues` (through `gh`) and each tool's version, last tag, last commit and commits since the tag (from the sibling checkouts). Everything else is curated by hand from each tool's `CLAUDE.md`, `docs/testing.md` and changelog: `plan.phases`, `handTests`, `ownerSpotTests`, `waitingOn`, `ownerActions`, `risks`, `sessions`. The date the page shows is not typed by anyone: the deploy writes the time of the last commit that changed `status.js` to `assets/dashboard/updated.json`, and the page reads it (and warns when it is more than 3 days old). Ages of requests count from today. `asOf` is only the fallback for a local copy.
- **Who updates it:** each tool's own session edits its tool's object in `status.js`, in the same piece of work as a change to the tool's status, and sets `checkedBy` (every tool repo's `CLAUDE.md` has a "Dashboard (EDGEweb)" section saying so, added 2026-11-16). So expect commits to `status.js` from other sessions: pull before editing it, and edit one tool's object at a time. A session working in EDGEweb checks those entries against the repos, runs `refresh.py` and sets `asOf`.
- **Refs for what waits on the owner (2026-11-23):** every entry of `ownerActions` is `{ "ref", "what", "since" }`, and each open entry of `ownerSpotTests` has `ref` and `since` too. A ref is the tool's two-letter `code` and a number (RA1, DR12); `since` is the day the item was first listed. Section 01 shows them as its ID and Since columns. The owner asks about an item by its ref: look it up in `status.js`, then read the tool's repo (its `CLAUDE.md`, `docs/testing.md`, issues) for the details, and ask the tool's session through `SendMessage` for what the repo does not say. A ref never changes and a number is never used twice: `ownerSeq` holds the tool's last number, and `python tools/dashboard/refresh.py --refs` (also part of a full refresh) gives a ref and today's date to any item without, a plain-text one included. A new tool needs its two letters in `CODES` in `refresh.py`. When the owner finishes an item (with a session, or by saying so), it stays in the file with `"done": "<date>"` added, and its row is struck through with the date; it no longer counts in the headline number. A spot test's `status` changes only to what the owner reported. The EDGEweb session also keeps the owner's **Owner Summary** artifact (a private claude.ai page of the summaries the owner asked for, by ref): a finished item gets a COMPLETED note and date there. `ownerSummary` at the top of `status.js` holds that page's `url` and the `refs` that have a summary there: Section 01 links those IDs to their entry (`url#REF`), so add a ref to the list when its summary is written.
- **Missing screenshots (2026-11-26):** Section 07 of the dashboard counts the placeholders left on the wiki and on `platform.html`, by tool and by who takes them: shots of the running game are the owner's, shots of the editor and the desktop are taken by a Claude session by script. `python tools/dashboard/shots.py` writes that count as `shots` in `status.js`; `--list` prints every missing shot; `--html <file>` also writes the **Image Dossier** page from `tools/dashboard/shots-dossier.html`, which is published to the private artifact at `shots.dossier` (read that artifact first, then publish to its `url`). The dossier gives each shot's file name, what it must show and where it ends up; the owner saves in-game shots under those names into the screenshot inbox. Who takes a shot is guessed from its description; correct a wrong guess in `tools/dashboard/shots-where.json`. Run the script after any change to a shot include or a `.shot` placeholder.
- **Nightly run:** the owner may have this session run a nightly routine (a session-only schedule that expires after 30 days and is lost when the session ends). Its steps, in order: (1) ask each tool's session for open hand tests that run in the editor only, and run them by script, REDnode first; (2) for every open request the dashboard lists, ask the session that owns it, by number, to resolve it that night, and record what each unresolved one waits on (the owner asked for this every night, 2026-11-27); (3) nudge them to bring their wiki pages and README up to date with the test runs and released features; (4) take the editor and desktop screenshots still missing, fill their placeholders, and run `shots.py` and republish the dossier; (5) run `refresh.py`; (6) write the results page for the morning, ending with the day the schedule expires so the owner can renew it. The standing rules hold: nothing marked passed here, no release, no deploy to the game, no screenshot of the owner's game. During the nightly run only, editor tests that need the owner's API keys may use them without asking (the owner's word, 2026-11-27): the tool reads the stored key itself, a key is never typed, printed or shown in a screenshot, and the results list each test that used one and roughly what it spent. Outside the nightly run, a key is used only for what the owner approved beforehand.
- Phase and test statuses use fixed words, which pick the colour: `done`, `built, tests pending`, `in progress`, `planned` for phases; `passed`, `not run`, `partly run`, `failed` for tests. Never mark a phase done or a test passed unless the tool's repo says so.
- `checkedBy` names the tool's own session that confirmed its entry, and when. An entry without it is a first pass by a reader, and the card says so.
- `sessions` holds the local session names seen in `ListAgents` when the file was written. Names change when a session restarts, so they are a hint to match on, not an address.
- Bump the `?v=` on the `status.js` script tag in `dashboard.html` when the file changes, as with `site.css`.

## Wiki (curated by Claude sessions)

- `docs/wiki/` is the EDGEmodders wiki at https://edgemodders.ai/wiki/. Claude sessions write and curate it; the community suggests changes on Discord or in issues (see `docs/wiki/contribute.md`). Terminology: the whole suite is the **EDGE platform**; REDagent, REDnode, REDcode, EDGEdeck and REDbridge are its core toolkits; EDGEbuilder, EDGEwave, EDGEmat, EDGEfab, EDGEquest, EDGEhack, EDGEdir, EDGEkit and EDGEchat build on them. Every section a page names must be in `wiki_sections`, or its pages drop out of the sidebar.
- `docs/wiki/first-hour.md` ("Your first hour") is the newcomer's route. The landing page's Get started button, the platform page, the wiki home and Getting started link to it.
- The wiki home (`docs/wiki/index.md`) introduces the EDGE platform. Its Platform benefits table is a summary of the Benefits lists on the toolkit pages: when a toolkit page's benefits change, update the summary too.
- Layout: `docs/_layouts/wiki.html` (sidebar built from page front matter) and the wiki rules at the end of `docs/assets/css/hud.css`. Sidebar groups are `wiki_sections` in `docs/_config.yml`.
- Every page needs front matter (quote `description` and any value containing ": ", or YAML breaks and the page drops out of the sidebar): `title`, `nav_title` (optional, sidebar label), `section` (one of `wiki_sections`), `order`, `description`, `reviewed` (date of the last check). One folder per toolkit, `index.md` as its overview.
- **Purpose:** each toolkit's wiki section is its user manual: user-focused, in depth and thorough. It draws on the toolkit's docs but does not copy them; the docs sites stay the developer reference and design record. EDGEdeck's section (`docs/wiki/edgedeck/`) is the agreed template. Pages, in sidebar order: Overview (what it is, what it's for, why you'd want it, how it fits EDGE, status, page map), Install and set up, one "using" page per feature area, Settings and commands (complete, from the extension's `package.json` where there is one), Troubleshooting. REDnode splits into using REDnode and making mods and apps. REDbridge, mostly invisible to users, gets a shorter section.
- **Screenshots:** use `{% include shot.html caption="..." shows="..." %}` wherever a picture helps; it renders a placeholder saying what the shot should show. The owner supplies images later: put them in `docs/assets/shots/<toolkit>/` and add `src="/assets/shots/<toolkit>/<name>.png"` to the include. Never take screenshots of the owner's game or PC unasked.
- **Screenshot inbox:** the owner saves screenshots into `docs/assets/shots/inbox/` (excluded from the site in `_config.yml`) and says they're there. Then: (1) look at each image (Read shows it) and match it to a placeholder by file name and content: `grep -rn 'include shot.html' docs/wiki` lists them all with their `caption` and `shows`; ask about any image that fits no placeholder or several, never guess. (2) Check each image for personal data: Windows user names in paths, Nexus or other account names, API keys, email addresses. Report anything found and publish that image only with the owner's OK. (3) Resize anything wider than 1600 px (PowerShell System.Drawing), save as PNG under `docs/assets/shots/<toolkit>/<page>-<what>.png`, and delete it from the inbox. (4) Add `src="..."` to the matching include and a real `alt` if the caption is not enough. (5) Commit, deploy, and report which placeholders are filled and which still wait.
- Sources of truth are the toolkits' own docs and CLAUDE.md files (read them with `gh api repos/Edgemodders/<repo>/contents/...` or the sibling checkouts, after a pull). The wiki explains and links; it does not copy reference material. Never state a feature works unless its repo says it passed or shipped; say "planned" or "untested" otherwise.
- **At a tool's release, its own session updates its pages here** (issue #9, asked of every Edgemodders repo on 2026-11-21): the tool's wiki section, its rows on shared pages (`wiki/library.md`, `wiki/glossary.md`, `wiki/first-hour.md`, `wiki/faq.md` and the like), and its card on `docs/index.html` and section on `docs/platform.html`. It works from the version's changelog, sets `reviewed` on each changed page, follows these rules, and pushes to `main` as `CyberbuildsAI`. The wiki describes the release, not a tool's `main`. The shared pages (the wiki home, Your first hour, the platform overview) stay with EDGEweb's session: a tool's session changes only its own rows there. So expect commits to the wiki from other sessions, and check them when curating.
- When curating: re-check each page touched against its sources, update `reviewed`, keep the toolkit statuses on `index.html` and `platform.html` consistent with the wiki, and answer recurring Discord or issue questions with FAQ entries or new pages.

## Conventions

- Commit straight to `main` and push, in small logical commits. Agree the plan in chat first.
- Changelog: `CHANGELOG.md` at the root, the convention shared by every Edgemodders repo (issue #2). Add a line under **Unreleased** (groups **New**, **Changed**, **Fixed**, **Other**) in the commit that makes a change a reader would notice. It stays out of the site, since Jekyll builds only `docs/`. A release (first: v0.1.0, 2026-11-12) renames **Unreleased** to `## <version> (<date>)`, tags `v<version>` and makes a GitHub release whose notes are that section.
- Git identity for this repo is `CyberbuildsAI` <340969962+CyberbuildsAI@users.noreply.github.com>, as in every EDGE repo: that account owns the GitHub organization, and Edgemodders is the organization, not a committer. Never change the global identity.
- **Writing files on this PC:** follow the section of that name in REDnode's `CLAUDE.md` (Windows, Git Bash, PowerShell 5.1). In short: write and change files with the Write and Edit tools, never through a Bash heredoc, `node -e`, `python -c` or `sed` (backslashes are lost, apostrophes break the shell); a script longer than one line goes in a file written with Write, then run; read the diff before committing. Every file here is LF (`.gitattributes`, 2026-11-26).
- Writing style: plain, short sentences, tables for comparisons. Friendly to non-modders: avoid jargon on the landing page, or explain it.
- House style is the HUD look shared with the RED* repos: tokens in `:root` (bg `#08090d`, yellow `#fcee0a`, cyan `#19f3ff`, red `#ff2a52`, green `#5dffa1`), Chakra Petch, Rajdhani, JetBrains Mono, cut-corner panels, sticky status bar. Keep it in sync with REDnode's design doc.
- `tools/brand/render.ps1` regenerates the banner, social preview, icon and badges. Tool icons in `docs/assets/tools/` are copied from each tool repo; recopy when they change.
- Always carry the "not affiliated with CD PROJEKT RED" notice, and credit WolvenKit and the wider modding community.
